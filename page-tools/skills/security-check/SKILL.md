# 🔒 보안 점검 스킬 (`security-check`)

> Claude Code 전용 로컬 스킬입니다 (Gemini와 공유하지 않음, `.agents/skills/`에 원본 없음).

**트리거:** `/security-check`, "보안 점검", "security check"

HTML/JS 파일을 4가지 보안 관점에서 점검하고, 발견된 문제를 심각도별로 분류하여 보고합니다.

---

## 📌 사용법

```text
/security-check [파일경로 또는 대상 설명]
```

**예시:**
- `/security-check`
- `/security-check secret-note.html`
- `보안 점검해줘`
- `security check app.js`

파일경로가 명시되지 않으면 현재 작업 중이거나 최근에 수정된 HTML/JS 파일을 우선 대상으로 삼고, 여러 개면 사용자에게 어떤 파일을 점검할지 확인합니다.

---

## 🧪 점검 항목 (4가지 관점)

### 1. 하드코딩된 비밀번호·API 키
소스 코드 내에 `password`, `pw`, `secret`, `apikey`, `api_key`, `token`, `key` 등의 변수명에 실제 값처럼 보이는 문자열 리터럴이 대입되어 있는지, 또는 `Authorization: Bearer ...`, `sk-...`, `AIza...` 같은 실제 키 형식 패턴이 코드에 그대로 박혀 있는지 확인합니다.
- 실제 자격 증명으로 보이는 값이 코드에 그대로 노출됨 → 🔴 심각 (저장소가 공개되거나 유출되면 즉시 계정/서비스 탈취로 이어짐)
- 테스트/더미 값이 명확하지만 이름이 오해를 살 수 있음 (예: `password = "1234"`가 실제 로그인 로직에 쓰임) → 🟡 주의
- 주석 처리된 예시 키, `.env.example`류의 플레이스홀더 → 🟢 제안 (실수로 실제 값이 들어갈 여지가 있으니 `.gitignore` 확인 권장)

### 2. escape 없이 innerHTML에 사용자 입력 삽입 (XSS)
`innerHTML`, `outerHTML`, `insertAdjacentHTML`, `document.write` 등에 사용자 입력(폼 값, URL 파라미터, `localStorage`, API 응답 등 신뢰할 수 없는 출처)이 이스케이프·새니타이즈 없이 그대로 대입되는지 확인합니다.
- 사용자 입력이 검증/이스케이프 없이 직접 `innerHTML` 등에 삽입됨 → 🔴 심각 (악성 스크립트 삽입 시 세션 탈취·피싱 등으로 이어지는 XSS 취약점)
- 입력 출처가 사용자 제어 가능성이 낮지만 습관적으로 `innerHTML`을 사용함 → 🟡 주의 (향후 입력 소스가 바뀌면 취약점화될 위험, `textContent`로 대체 권장)
- 이미 이스케이프 함수를 거쳤으나 커스텀 구현이라 신뢰도가 낮음 → 🟢 제안 (검증된 라이브러리 사용 권장)

### 3. console.log의 민감정보 노출
`console.log`, `console.debug`, `console.info`, `console.warn` 등에 비밀번호, 토큰, API 키, 개인정보(주민번호·전화번호·이메일 등), 전체 요청/응답 객체 등이 출력되는지 확인합니다.
- 비밀번호·토큰·API 키 등 자격 증명을 직접 로그로 출력 → 🔴 심각 (브라우저 콘솔·로그 수집 시스템을 통해 유출)
- 개인정보(이름, 이메일, 전화번호 등)나 전체 사용자 객체를 로그로 출력 → 🟡 주의
- 디버깅용으로 보이는 일반 상태값 로그가 배포 코드에 남아있음 → 🟢 제안 (배포 전 제거 권장)

### 4. http://로 시작하는 외부 요청
`fetch(...)`, `XMLHttpRequest`, `<script src=...>`, `<img src=...>`, `<link href=...>`, `axios.get(...)` 등에서 `http://`로 시작하는(HTTPS가 아닌) 외부 리소스/API 요청이 있는지 확인합니다.
- 로그인·결제 등 민감한 데이터를 주고받는 요청이 `http://`로 되어 있음 → 🔴 심각 (평문 전송으로 중간자 공격(MITM)에 노출)
- 민감하지 않은 정적 리소스(이미지 등)가 `http://`로 되어 있음 → 🟡 주의 (Mixed Content 경고, 일부 브라우저에서 차단 가능)
- `localhost`/내부망 대상의 `http://` 호출 → 🟢 제안 (개발 환경 한정이면 낮은 위험이나 배포 전 확인 권장)

## ⚙️ 실행 절차 (Workflow)

### 1단계: 대상 파일 확정
1. 사용자가 지정한 파일 또는 현재 작업 중인 HTML/JS 파일을 확인합니다.
2. 파일을 읽습니다.

### 2단계: 4가지 항목 점검
1. 위 점검 항목 1~4를 순서대로 검사합니다.
2. `<script>` 태그 내부 인라인 JS와 별도 `.js` 파일 모두 검사 대상에 포함합니다.
3. 각 항목에서 발견된 문제를 심각도(🔴/🟡/🟢)와 함께 정확한 근거(파일명:라인번호, 해당 코드 스니펫)로 기록합니다.

### 3단계: 결과 보고
아래 형식으로 심각도 그룹별로 묶어서 보고합니다. 문제가 없는 항목은 🟢 통과로 짧게 표시합니다.

```text
## 🔒 보안 점검 결과 — <파일명>

🔴 심각 (N건)
- [항목명] 구체적인 문제 설명 (파일:라인)
  근거: `코드 스니펫`

🟡 주의 (N건)
- [항목명] 구체적인 문제 설명 (파일:라인)
  근거: `코드 스니펫`

🟢 제안 / 통과
- [항목명] 문제 설명 또는 "이상 없음" (파일:라인)
```

### 4단계: 다음 단계 안내
- 🔴 심각 항목이 있다면 즉시 수정할지 사용자에게 물어보고, 동의하면 수정 후 `/commit` 스킬로 이어지도록 안내합니다.
- 수정할 파일이 여러 개인 경우, 파일별로 위 보고 형식을 반복합니다.
- 이 스킬은 점검·보고만 수행하며, 사용자 승인 없이 코드를 임의로 수정하지 않습니다.
